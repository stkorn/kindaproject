# ADR-006: นิยามรายได้ VAT และ GP

- สถานะ: Accepted
- วันที่: 2026-11-04

## บริบท
bronze มีเฉพาะ `total_price_incl_vat_thb` ซึ่งเป็นยอดที่ลูกค้าจ่าย ยอดนี้ไม่ใช่รายได้ของร้านเพราะมี VAT รวมอยู่ และเงินที่ platform โอนเข้าบัญชีก็เป็นอีกตัวเลขหนึ่ง
marts ทุกตัวใน M2 ต้องใช้นิยามเดียวกัน และสูตรที่ผิดนิยามจะรันผ่านโดยไม่มี error จึงต้องตกลงให้ชัดก่อนเขียน SQL

การปัดเศษส่งผลกับตัวเลขจริง จากบิล completed ของ BKK02 เดือนตุลาคม 2026 (9,710 บิล, 931,938.00 บาท):

| วิธี | รายได้ก่อน VAT |
|---|---|
| ปัดทีละบิลแล้วรวม | 870,967.28 |
| รวมทั้งเดือนแล้วค่อยปัด | 870,970.09 |

## ทางเลือก
**grain ของการปัดเศษ**
1. ปัดทีละบิลแล้วรวม: ยอดทุกระดับรวมกันตรงกัน และย้อนกลับไปถึงบิลได้ แต่ต้องเก็บคอลัมน์เพิ่ม
2. รวมยอดก่อนแล้วค่อยปัดในแต่ละรายงาน: เขียนง่าย แต่ยอดรายวันรวมกันไม่เท่ากับยอดรายเดือน

**ที่อยู่ของสูตร**
1. `stg_orders`: ผิดหลักของ staging ที่ไม่ใส่กฎธุรกิจ
2. แต่ละ mart เขียนสูตรเอง: ตัวเลขมีโอกาสไม่ตรงกันระหว่างรายงาน
3. `fct_orders` ตารางเดียว แล้ว mart อื่น `SUM` ต่อ

## ตัดสินใจ
ปัดเศษแบบ **1** และเก็บสูตรแบบ **3**: `fct_orders` มี grain หนึ่งแถวต่อหนึ่งบิล รวมบิลที่ยกเลิก และคำนวณทุกค่าที่นี่

| คอลัมน์ | สูตร | ตัวอย่างบิล Grab 107.00 |
|---|---|---|
| `gross_incl_vat_thb` | `total_price_incl_vat_thb` | 107.00 |
| `net_excl_vat_thb` | `round(gross / 1.07, 2)` | 100.00 |
| `vat_thb` | `gross - net` | 7.00 |
| `gp_excl_vat_thb` | `round(net × gp_rate, 2)` | 30.00 |
| `vat_on_gp_thb` | `round(gp × 0.07, 2)` | 2.10 |
| `payout_thb` | `gross - gp - vat_on_gp` | 74.90 |
| `revenue_thb` | `net` เมื่อ `status = 'completed'` ไม่งั้น `0` | 100.00 |

- **รายได้** = `SUM(revenue_thb)` นับเฉพาะบิล `completed` จึงถูกต้องแม้ไม่กรอง status ส่วน `COUNT` และ `AVG` ยังต้องกรองเอง
- `net_excl_vat_thb` เป็นยอดของบิลทุกสถานะ ไม่ใช่รายได้ · `fct_orders` เก็บบิลที่ยกเลิกไว้ให้ reconciliation ใน M7 และการวิเคราะห์อัตรายกเลิก
- `vat_thb` เป็นผลลบ ไม่ใช่การปัดอีกครั้ง จึงรับประกันว่า `gross = net + vat` ทุกบิล
- `walk_in` ใช้สูตรเดียวกัน เพราะ `gp_rate = 0` ทำให้ `payout = gross`
- อัตรา VAT 7% กำหนดที่เดียวเป็นตัวแปรของ dbt ส่วน `gp_rate` มาจาก `config/business.yaml`
- mart ห้ามคำนวณ VAT หรือ GP ซ้ำ ให้ `SUM` จาก `fct_orders`

**สมมติฐานของโปรเจค** (ข้อมูลเป็นการจำลอง ไม่ได้มาจากสัญญาจริง)
- GP คิดจากฐานก่อน VAT และ platform เก็บ VAT 7% บนค่า GP
- ทุกสาขาจดทะเบียน VAT
- ธุรกิจจริงต้องตรวจเงื่อนไขนี้จากสัญญาและ statement ของ platform

## ผลที่ตามมา
- ใบกำกับภาษีเกิดรายบิล แต่ยื่น ภ.พ.30 รายเดือน ยอดที่ยื่นจึงย้อนกลับไปถึงแต่ละบิลได้
- `SUM` ทุกระดับ (วัน, สาขา, ช่องทาง) ตรงกันเสมอ
- เงินสดรับ รายได้ และ VAT เป็นคนละตัวเลขที่กระทบยอดกันได้: `payout - (vat - vat_on_gp) = net - gp` เช่น 74.90 - 4.90 = 70.00
- DQ test ที่ได้จากนิยามนี้ (M2):
  - `gross = net + vat` และ `payout = gross - gp - vat_on_gp` ทุกบิล
  - `abs(net × 1.07 - gross)` ไม่เกินค่าคลาดเคลื่อนจากการปัดเศษ
  - `gp = 0` เมื่อเป็น `walk_in`
  - `revenue = 0` เมื่อ `status` ไม่ใช่ `completed`
  - ยอดรายได้ใน mart รวมกันเท่ากับ `SUM(revenue_thb)` ของ `fct_orders`
- ตอนเขียน SQL ต้องตรวจว่าการหารไม่ผ่าน float เพราะ engine บางตัวแปลงผลหารของ decimal เป็น `DOUBLE`
- นิยาม royalty และ COGS ยังไม่อยู่ใน ADR นี้ ให้ตัดสินใจตอนทำ mart นั้น

**ทบทวนเมื่อ**: ต้องการรายได้ก่อน VAT ระดับเมนู (ผลรวมของรายการที่ปัดแล้วอาจไม่เท่ากับค่าระดับบิล จึงต้องมีกฎปันส่วน),
statement ของ platform ปัดเศษต่างจากเรา, มีส่วนลดหรือค่าส่ง (เกี่ยวกับ ADR-003), อัตรา VAT เปลี่ยน หรือมีแฟรนไชส์ที่ไม่ได้จด VAT
